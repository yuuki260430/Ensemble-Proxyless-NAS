# CIFAR-10 化とアンサンブル探索：作業記録と論文用メモ

最終更新: 2026-10-08

ProxylessNAS を CIFAR-10 / RTX 5080 で動かすための変更、アンサンブル用に追加した機能、supernet 学習の調査と改善、実験結果、論文に書くべき引用と手法上の注意点をまとめたもの。

## 1. 実行環境

| 項目 | 内容 |
|---|---|
| GPU | NVIDIA GeForce RTX 5080（Blackwell, sm_120, 16GB）, driver 580 |
| venv | `env5080`（Python 3.12） |
| PyTorch | 2.11.0+cu128 / torchvision 0.26.0+cu128（`https://download.pytorch.org/whl/cu128` から導入） |
| その他 | PyYAML 導入、torchaudio 削除（未使用） |

- RTX 5080 には **cu128 以降のビルドが必須**。torch 2.6.0+cu124 はインストール自体は成功するが、GPU 演算が `no kernel image is available` で失敗する。
- 新しい PyTorch では `torch.optim.Adam` の `betas` 型チェックが厳しいため、`--arch_adam_beta1` の既定値を `0` → `0.0` に変更した。
- 既知の問題：1 回だけ `libnvrtc.so.12` 内でセグメンテーション違反が発生（試運転 7 回中 1 回、以降の長時間実行では発生なし）。`cudnn.benchmark=True`（[run_manager.py](run_manager.py)）時の実行時カーネルコンパイルが疑わしい。再発したら `--resume` で再開し、頻発するなら benchmark 無効化か cu130 版を試す。

| [configs/config_5080.yaml](configs/config_5080.yaml) | compute capability 12.0、メモリ 16GB に修正 |

### FLOPs 基準値の根拠
公式の proxyless_mobile / gpu / cpu を、ImageNet 設定（224 入力、stem stride 2）と上記 CIFAR 設定（32 入力、stem stride 1、第 1 段 stride 1）で比べると、FLOPs 比はそれぞれ 0.302 / 0.298 / 0.285 だった。そこで ImageNet の基準値に 0.30 を掛けた（1.00× で 300M → 90M）。

### mobile レイテンシを使わない理由
公式の mobile レイテンシ表（`mobile_trim.yaml`）は 224×224 入力の ImageNet 形状でしか計測されていない。32×32 入力の値は存在しないため、CIFAR-10 ではハードウェア制約として FLOPs のみを使う。

## 3. アンサンブル用に追加したスクリプト

### 3.1 [cifar10_derive_archs.py](cifar10_derive_archs.py)：1 回の探索から複数構造を取り出す
探索のチェックポイントのアーキテクチャパラメータ α から K 個の構造を取り出し、`learned_net` と同じ形式（`net.config` / `run.config` / `init`）で書き出す。

- 候補の生成（`--mode`）
  - `topk`：同時確率 ∏ softmax(α) の上位 K 個（ビームサーチで厳密に計算）
  - `sample`：softmax(α / T) からサンプリング
- 絞り込み：`--min_flops` / `--max_flops`、`--min_hamming`（構造どうしの最小相違ブロック数）
- 選択（`--select`）
  - `order`：条件を満たした候補を先頭から K 個
  - `dpp`：`--pool_size` 個の候補を評価し、NEAS の Diversity Score で K 個を選ぶ（下記）
- `arch_00` は常に最も確率の高い構造（`--no_argmax` で解除）。既存の `learned_net/net.config` と一致することを確認済み。

**`--select dpp` の処理**（NEAS [4] の Eq.4, 5, 7, 8 をモデル単位に適用）

1. 各候補を supernet の継承重みで作り、BN 統計を学習データで再計算（NEAS [4]、SPOS [9] と同様）
2. 品質 r_p：学習データのうち、検証用 5,000 枚とは別の 2,000 枚での top-1 精度
3. 類似度 S_pq = E_n[ exp(−β ‖v_p(n) − v_q(n)‖₂) ]。v は最終層直前の 1280 次元特徴。β の既定は全ペアの平均距離の中央値の逆数
4. L = diag(r^γ) · S · diag(r^γ) として、det(L_部分集合) が最大になる K 個を貪欲法で選ぶ

**diag(r) の意味（説明用）**

- **diag(r)**：品質のベクトル r = (r_1, …, r_P) を対角線上に並べた対角行列（ほかの要素は 0）。左から掛けると p 行目が r_p 倍、右から掛けると q 列目が r_q 倍になる。なお `numpy` の `np.diag` はベクトルを渡すと対角行列を作り、行列を渡すと対角要素を取り出すが、ここでの diag(r) は前者の意味
- **L の中身**：両側から挟むと L_pq = r_p · S_pq · r_q
  - 対角要素 L_pp = r_p²（S_pp = 1 なので、候補単体の良さだけが残る）
  - 非対角要素 L_pq = r_p r_q S_pq（2 つの候補の「重なり」。品質が高く、かつ似ているほど大きい）
- **数値例**（`Exp3/derive/dpp5` で最初に選ばれた 2 つ。r = (0.913, 0.892)、類似度 s = 0.360）

  ```
  diag(r)          S                diag(r)          L
  [0.913  0    ]   [1      0.360]   [0.913  0    ]   [0.834  0.293]
  [0      0.892] × [0.360  1    ] × [0      0.892] = [0.293  0.796]

  det(L) = 0.834 × 0.796 − 0.293² = 0.577
         = 0.913² × 0.892² × (1 − 0.360²)   ← 品質の項 × 多様性の項
  ```

- **Q. なぜ品質と多様性に分けられるのか**：det(AB) = det(A) det(B) と、対角行列の行列式は対角要素の積、という 2 つの性質から
  det(L_Y) = det(diag(r_Y)) · det(S_Y) · det(diag(r_Y)) = (∏_{p∈Y} r_p)² · det(S_Y)
  となり、品質だけの項と類似度だけの項に分かれる。DPP の標準的な quality–diversity decomposition（Kulesza & Taskar [6]）で、NEAS も同じ形
- **Q. なぜ片側ではなく両側から挟むのか**：L を対称・半正定値に保つため。DPP のカーネルは半正定値である必要がある。片側だけの diag(r)·S は L_pq = r_p S_pq と L_qp = r_q S_qp が一致せず対称にならない。両側から挟んだ D S D（D は対角行列）は、S が半正定値なら必ず半正定値になる。S は Laplacian カーネル exp(−β‖·‖₂)（正定値カーネル）の平均なので半正定値
- **Q. なぜ品質が 2 乗で効くのか**：左右で 1 回ずつ r_p が掛かるため
- **Q. 幾何学的な意味は**：各候補を長さ r_p、向き φ_p（長さ 1）のベクトル b_p = r_p φ_p と見ると、S_pq = φ_p·φ_q（向きの内積）、L_pq = b_p·b_q となり、L はグラム行列。det(L_Y) は選んだベクトルが張る平行多面体の体積の 2 乗。diag(r) はベクトルの長さ（品質）、S は向き（似ているかどうか）を決める。長くてばらばらの向きのベクトルを選ぶほど体積が大きい
- **Q. 本手法の diag(r^γ) は何が違うのか**：対角要素を r_p^γ にしただけで構造は同じ。品質の項が (∏ r_p)^{2γ} になり、γ を大きくするほど品質の違いが強く効く。NEAS の γ·r（定数倍）では全ベクトルが同じ倍率で伸びるだけなので、体積の大小関係も選択も変わらない（7.1）
- **一言で説明するなら**：「diag(r) は品質を対角に並べた行列で、類似度行列 S を両側から挟むことで、各候補の品質で S を重み付けしています。こうすると行列式が『品質の積の 2 乗 × 類似度行列の行列式』に分かれるので、品質が高く互いに似ていない組み合わせほどスコアが大きくなります。両側から挟むのは、カーネルを対称・半正定値に保つためです。」

### 3.2 [cifar10_ensemble_eval.py](cifar10_ensemble_eval.py)：アンサンブルの評価
- 各モデルの softmax 出力を平均する（Deep Ensembles [10] と同じ平均方式）
- 出力する指標：各モデルの精度と NLL、先頭 m 個のアンサンブルの精度（m=1…K）、oracle 精度、予測の食い違い率（ペアごと）、合計 FLOPs・合計パラメータ数
- `--split valid` では学習時と同じ固定 5,000 枚を使う。組み合わせの決定は valid、最終報告は test と使い分ける

### 実行例
```bash
source env5080/bin/activate
# 探索（fair ウォームアップ付き。4 章参照）
python search/cifar10_arch_search.py --path Exp3/search --gpu 0 --warmup_epochs 70 --warmup_fair \
  --n_epochs 150 --dropout 0.3 --hw-config search/configs/config_5080.yaml
# 構造の取り出し
python search/cifar10_derive_archs.py --search_path Exp3/search --out_path Exp3/ensemble_dpp \
  --n_archs 3 --mode sample --select dpp --pool_size 30
# 各構造の再学習
for d in Exp3/ensemble_dpp/arch_*; do
  python search/cifar10_run_exp.py --path $d --train --gpu 0 --hw-config search/configs/config_5080.yaml > $d/train.log 2>&1
done
# 評価
python search/cifar10_ensemble_eval.py --paths Exp3/ensemble_dpp/arch_* --output Exp3/ensemble_dpp/ensemble_test.json
```

注意：`cifar10_run_exp.py` の `--path` には `net.config` があるフォルダを指定すること。探索の出力フォルダ（例：`Exp2/proxyless_gpu`）を指定すると、ImageNet 用の構造と重みが読み込まれて size mismatch になる。

## 4. supernet 学習の調査と改善

### 4.1 症状
最初の探索（5.1 節）で、supernet の精度がウォームアップ 20 エポックで 20%、探索終了時でも 58% にとどまった。同じ構造を固定ネットワークとして学習すると 89% に達する。

### 4.2 見つかった実装上のバグ（コミット `1e7eaa4` で修正）
どちらも、最初に取り込んだ元のコード（`a195216`）から変更していない部分にあった。

1. **探索フェーズで候補演算の重みが学習されない**（[modules/mix_op.py](modules/mix_op.py) の `ArchGradientFunction`）
   - `full_v2` モードの backward が `torch.autograd.grad(output, detached_x)` で入力の勾配だけを返しており、候補演算の重みに勾配が届いていなかった（0/162 パラメータ）。
   - そのため最初の探索では、探索フェーズ 150 エポックの間、stem・最初の固定ブロック・feature_mix・分類層と α だけが学習され、候補演算はウォームアップ時点の重みのままだった。
   - `torch.utils.checkpoint` と同じ方式（backward 内で `torch.autograd.backward`）に修正。通常の自動微分と勾配が一致することを確認（194/194 パラメータ、float64 で相対誤差 2.5e-16）。
2. **選ばれなかった候補演算に古い勾配が残る**（[nas_manager.py](nas_manager.py)）
   - `net.zero_grad()` を、使わない候補を `unused_modules_off()` でモデルから外した後に呼んでいたため、外れた演算の勾配が消えず、`optimizer.step()` で繰り返し適用されていた。
   - 更新前に `optimizer.zero_grad()` を追加。効果は小さかった（ウォームアップ 1 エポックの学習精度 10.7% → 11.9%）。

### 4.3 立ち上がりの遅さの切り分け
最小の学習ループ（1 エポック = 174 ステップ、学習精度はステップ 100〜174 の平均）で比較した。

| 条件 | 学習 top-1 |
|---|---|
| 固定ネットワーク、ランダム初期値から（参考：3 エポックで検証 64%） | 1 エポックで検証 46% |
| supernet・経路を固定 | 41% |
| supernet・2 経路を交互 | 31% |
| supernet・毎ステップ一様ランダム（元の方式） | 11% |
| 同上で lr 1/10 / モーメンタムなし / Zero 除外 | 10〜12% |

- 経路の切り替えの仕組みは正常。経路の選択肢が増えるほど立ち上がりが遅くなる。各層の候補は重みを共有しない別々の演算なので、下流の層は上流の 6〜7 通りの出力すべてに対応する必要がある。
- ImageNet（1 エポック約 5,000 ステップ、元論文のウォームアップ 40 エポックで約 20 万ステップ）と比べ、CIFAR-10（1 エポック約 175 ステップ、ウォームアップ 20 エポックで約 3,500 ステップ）は**更新ステップ数が約 1/57** しかない。ウォームアップをエポック数で決めると、CIFAR-10 ではほとんど学習されないまま探索が始まる。

### 4.4 ウォームアップを延ばした場合（`Exp3/warmup150`）
一様ランダムのまま 150 エポック（約 26,000 ステップ、約 55 分）に延ばすと、検証 46.1% / 学習 50.5% で頭打ちになった。学習精度が低いので過学習ではなく、当てはめきれていない。ステップ数を増やすだけでは不十分。

### 4.5 FairNAS 型のウォームアップ（`--warmup_fair`、コミット `a0a6b4f`）
FairNAS [15] の strict fairness を参考に、1 回の更新ごとに、各層の全候補を 1 回ずつ使う m 本の経路（m = 7）で勾配を貯めてから更新する。

- `fair_paths()`：全 21 層の全候補を 1 回ずつ含む 7 本の経路を作る。候補が 6 個の層（21 層中 6 層）では、残り 1 本をランダムに選ぶ
- `average_fair_grads()`：各パラメータの勾配を、そのパラメータが使われた回数で割る（共有部分は 7 本の平均、候補演算は通常 1 本分）
- 1 エポックの学習時間は約 78 秒（一様ランダムの約 6.5 倍）

**比較結果（ほぼ同じ計算時間）**

| | 所要時間 | 検証 top-1 | 学習 top-1 |
|---|---|---|---|
| 一様ランダム 150 エポック（`Exp3/warmup150`） | 約 55 分 | 46.1% | 50.5% |
| **fair 35 エポック（`Exp3/fair35`）** | **約 46 分** | **62.4%** | **64.8%** |

- fair は 10 エポック（約 13 分）で 46.7% に達し、一様ランダム 55 分の最終値を約 1/4 の時間で上回った
- 学習精度 64.8% なので、まだ当てはめきれていない。エポック数を増やせば伸びる余地がある

## 5. 実験結果

### 5.1 最初のアーキテクチャ探索（`Exp2/proxyless_gpu`）※4.2 節のバグの影響あり
- 設定：ウォームアップ 20 エポック + 探索 150 エポック、batch 256、lr 0.05（cosine）、dropout 0.3、`--target_hardware None`、勾配法（`full_v2`）
- 所要時間：約 65 分（ウォームアップ約 8 分 + 探索約 57 分、ログの時刻と 1 反復あたりの時間から推定）

| 時点 | supernet 検証 top-1 |
|---|---|
| ウォームアップ 20/20 | 20.5% |
| 探索 150/150 | 58.3%（最高 58.6%） |

- 探索終了時の α のエントロピーは 1 ブロックあたり平均 1.62（全 21 ブロック合計 34.1）。一様分布なら平均 1.90（候補 7 個のブロックは ln 7、6 個のブロックは ln 6）なので、確率分布はまだほぼ一様
- 得られた構造：163.0M FLOPs、3.28M パラメータ
- **候補演算の重みがほぼ学習されていない supernet 上で α を更新しているため、この探索結果の構造選択には信頼性がない。アンサンブル実験には使わず、修正後のコードで探索し直す**

### 5.2 5.1 の構造の再学習（`Exp2/cifar10_retrain`）
- 設定：`learned_net/run.config` を使用（150 エポック、lr 0.05、label smoothing 0.1、wd 4e-5）。supernet の継承重みから学習開始
- 所要時間：約 45 分

| | top-1 |
|---|---|
| 学習前（継承重みのまま） | テスト 59.4% |
| 再学習後（150 エポック） | **検証 89.16%（最高 89.46%）/ テスト 89.10%** |

→ 暫定の単体ベースライン：テスト 89.10%、163.0M FLOPs、3.28M パラメータ（構造は 5.1 のバグありの探索で選ばれたもの）

### 5.3 構造の取り出し（5.1 の supernet での動作確認のみ、再学習は未実施）
- `topk`：最も確率の高い構造から 1〜2 ブロックしか違わない。`--min_hamming 4` で 4 ブロック以上違う組み合わせにできる
- `sample`：最も確率の高い構造から 12〜16 ブロック違い、ほぼランダム
- `dpp`（候補 12 個から 3 個）：選ばれた 3 構造の類似度は 0.37〜0.39（候補全体では 0.32〜0.60）。類似度が最も低い候補（0.32）は品質 56% と低いため選ばれず、品質と多様性の両方が考慮されている
- 継承重みのまま 3 構造をアンサンブルしても、テスト精度 59.0%（単体 59.4%）で向上しない。重みを共有しているため誤りも似ていると考えられ、効果は再学習後に評価する必要がある

### 5.4 修正後の探索（`Exp3/fair70_search`）
- 設定：`--warmup_fair --warmup_epochs 70 --n_epochs 150 --dropout 0.3`、`--target_hardware None`（FLOPs 制約なし）
- 所要時間：約 146 分（ウォームアップ 92 分 + 探索 54 分、9/30 15:05〜17:31）

| | 5.1 の探索（バグあり） | 修正後（fair 70 + 探索 150） |
|---|---|---|
| ウォームアップ終了時の supernet 検証 top-1 | 20.5% | 70.9% |
| 探索終了時の supernet 検証 top-1 | 58.3%（最高 58.6%） | 82.1%（最高 82.9%） |
| α のエントロピー（1 ブロック平均、一様なら 1.90） | 1.62 | 1.39（150 エポックの間ずっと減少中で、収束しきっていない） |
| 各ブロックで最も選ばれやすい候補の確率（平均） | 0.37 | 0.51 |
| 得られた構造 | 163.0M FLOPs / 3.28M パラメータ | 148.5M FLOPs / 2.19M パラメータ |

- 選ばれた構造：ブロック 1〜14 はほぼすべて 7x7_MBConv6、後半の 4 ブロックは Zero（スキップ）。FLOPs 制約がないため、最も大きい候補が選ばれやすい

### 5.5 修正後の構造の再学習（`Exp3/fair70_retrain`）
- テスト top-1 **90.63%**（検証 90.84%、最高 90.86%）、148.5M FLOPs、2.19M パラメータ
- 5.2（テスト 89.10%、163.0M FLOPs、3.28M パラメータ）より精度が高く、モデルも小さい → 新しい単体ベースライン

### 5.6 修正後の supernet からの構造の取り出し（`Exp3/derive/`、各 5 個）

| 選び方 | 構造どうしの相違ブロック数 最小 / 平均 / 最大 | FLOPs |
|---|---|---|
| `topk5`（確率の高い順） | 1 / 1.5 / 2 | 145〜157M |
| `topk_h4`（`--min_hamming 4`） | 4 / 4.0 / 4 | 148〜164M |
| `sample5`（サンプリング） | 5 / 12.6 / 18 | 139〜159M |
| `dpp5`（候補 30 個から DPP で選択） | 5 / 11.7 / 16 | 138〜159M |

- `dpp5` の選ばれた 5 構造の類似度は 0.35〜0.41（候補全体は 0.34〜0.68）、品質（学習データの一部での精度）は 89.1〜91.3%（候補全体は 87.1〜91.3%）。多様性と品質を両立
- 品質の値は 5.1 の supernet では 56〜63% だったが、修正後は 87〜91% になり、候補の良し悪しを比べる精度が上がった

### 5.8 考察
1. **初期値の影響が最も大きい**：単体精度はほぼ同じ（90〜91%）だが、アンサンブルによる向上はスクラッチ +1.7〜1.9、ファインチューニング +0.8〜0.9。予測の食い違いもスクラッチ約 10%、ファインチューニング 7〜8%。全メンバーが同じ supernet の重みから始まると誤り方が似る。再学習時間は同じ 150 エポックなので、ファインチューニングにコスト面の利点もない → **アンサンブルのメンバーはスクラッチから学習する**
2. **スクラッチでは構造の多様性の効果が見えない**：seed 92.43%、dpp 92.45%、topk 92.57% で差は誤差の範囲。ランダムな初期値だけで約 10% の食い違いが生まれ、構造を変えても多様性はほとんど増えていない
3. ファインチューニングでは dpp が食い違い（8.03% 対 6.79%）と oracle で seed を上回ったが、初期値による多様性がない条件で構造が補った形で、1 の結論からは実用上の意味が薄い
4. **研究の主張への影響**：今回の条件（CIFAR-10、この探索空間、3 モデル、FLOPs がほぼ同じ構造どうし）では、「構造が多様なアンサンブルは seed だけ変えたアンサンブルより良い」とは示せていない。dpp で選ぶ利点も、スクラッチでは確認できていない
5. 今回取り出した構造は、どれも FLOPs 140〜160M・7x7_MBConv6 中心の似た構造だった。構造の違いが小さすぎた可能性がある

### 5.9 比較実験（5.7）の解説

**目的**：「構造の違うモデルを集めたアンサンブルは、同じ構造を学習し直しただけのアンサンブルより良いか」を確かめる。これが言えれば、ProxylessNAS で多様な構造を選ぶことに意味があると主張できる。

**実験の組み立て**：2 つの条件を掛け合わせた 2 × 3 = 6 通りのアンサンブル（各 3 モデル）

| 条件 | 水準 | 内容 |
|---|---|---|
| 構造の選び方 | seed | 同じ構造（`arch_00`）を seed 0/1/2 で 3 回学習。**比較の基準**（構造は同じで、学習の乱数だけが違う） |
| | dpp | `arch_00` + NEAS のスコアで選んだ 2 構造（提案手法） |
| | topk | `arch_00` + 確率の高い順で 4 ブロック以上違う 2 構造（単純な選び方） |
| 初期値 | ファインチューニング | supernet で学習済みの重みから再学習 |
| | スクラッチ | ランダムな初期値から再学習 |

3 種類とも `arch_00` を共通のメンバーにしているので、違いは残り 2 つの選び方だけになる。

**指標の読み方**

| 指標 | 意味 | 良い方向 |
|---|---|---|
| アンサンブル精度 | 3 モデルの softmax を平均したときのテスト精度 | 高い |
| 向上幅 | アンサンブル精度 − メンバー中の最高精度 | 大きい |
| NLL | 予測の確信度がどれだけ正しいか（外れているのに自信満々だと悪化） | 低い |
| 食い違い率 | 2 モデルの予測クラスが違う画像の割合（ペアの平均）。メンバーの多様性 | 高い |
| oracle 精度 | 3 モデルのうち 1 つでも正解した画像の割合。アンサンブルで届きうる上限の目安 | 高い |

アンサンブルは、メンバーが**それぞれ正確で、かつ違う間違え方をする**ときに効く。全員が同じ画像で同じように間違えるなら、平均しても直らない。

**分かったこと**

1. **初期値の違いが、構造の選び方よりずっと大きく効いた**
   - 向上幅はスクラッチ +1.7〜1.9、ファインチューニング +0.8〜0.9 で約 2 倍。食い違い率もスクラッチ約 10%、ファインチューニング 7〜8%
   - ファインチューニングでは 3 モデルとも同じ supernet の重みから始まるため、学習後も似た解に落ち着き、間違え方が似る。スクラッチでは出発点がばらばらなので、自然に違う間違え方をする
   - 再学習時間は同じなので、ファインチューニングにコスト面の利点もない → **メンバーはスクラッチから学習すべき**
2. **スクラッチでは、構造を変えても効果が見えなかった**
   - seed 92.43%、dpp 92.45%、topk 92.57% で、差は最大 0.14 ポイント
   - 誤差の範囲と言える根拠：(a) 同じ構造を seed だけ変えた単体精度が 90.72 / 90.31 / 90.28% と 0.44 ポイント揺れている、(b) 92% 前後の精度をテスト 10,000 枚で測ると標準誤差は約 0.26 ポイント
   - 食い違い率も seed と dpp が同じ 10.02%。ランダムな初期値だけで十分に違う間違え方をしており、構造を変えても多様性がほとんど増えなかった
3. **ファインチューニングでは、構造の違いが多様性を補った**
   - dpp は食い違い率（8.03% 対 6.79%）と oracle（94.85% 対 94.34%）で seed を上回った
   - ただし 1 のとおりファインチューニングを使う理由がないため、実用上の意味は薄い

**研究としての意味**
- 示せたこと：バグ修正と FairNAS 型ウォームアップで探索が機能するようになった（単体 89.10% → 90.63%、モデルも小さくなった）。3 モデルのアンサンブルで約 +1.8 ポイント向上する。メンバーはスクラッチから学習すべき
- 示せていないこと：「構造が多様なアンサンブルは seed 違いのアンサンブルより良い」こと
- 考えられる理由：今回の構造はどれも FLOPs 140〜160M、前半が 7x7_MBConv6 中心のよく似た構造だった（FLOPs 制約なしで探索したため）。構造の違いが小さすぎて、初期値の違いに埋もれた可能性がある
- 次の一手：6.2 節の計画 B（大きさの違う構造を混ぜる）で差が出れば、「同じ総 FLOPs なら、小さく多様なモデルを集めた方が良い」という形で主張を立て直せる

**A. 学習の繰り返し（スクラッチのみ、14 モデル、約 11 時間）**
- 目的：5.7 のスクラッチ 3 条件（seed / dpp / topk）の差が誤差を超えるかを確かめる
- 方法：各条件について、seed の組み合わせを変えたアンサンブルを 3 組ずつ作り、平均と標準偏差で比べる

- 夜間に流すのが効率的

**B. FLOPs 制約付きの探索で、大きさの違う構造を混ぜる（2026-10-07 開始、`Exp4/`）**
- 目的：構造の多様性が効きうる条件を探す。5.8 の 5 のとおり、今回の構造は似すぎていた
- 狙う主張：「同じ総 FLOPs なら、小さく多様なモデルを集めた方が、大きな単体や同じ構造の seed アンサンブルより良い」
- **方針の修正**：当初は FLOPs の目標値を変える予定だったが、ProxylessNAS の正則化（`mul#log`）は CE × α (log FLOPs / log T)^β で、目標 T は対数の中にしか入らない。T を 40M → 100M にしても α を動かす力は約 1.5% しか変わらず、T は「近づける目標」として働かない。構造の大きさを実際に変えるのは罰則の強さ β（`--grad_reg_loss_beta`、既定 0.3）
- 方法：`--target_hardware flops`（T = 90M）で β = 0.3 / 1.0 / 3.0 の 3 通りを探索し、得られる構造の FLOPs を確かめる
  - 3 つとも `Exp3/fair70_search` のウォームアップ済み supernet（`warmup.pth.tar`）から `--resume` で探索フェーズだけを実行（ウォームアップ 92 分を省略、比較条件もそろう）。1 回約 55 分
  - 実行スクリプト：`Exp4/search_queue.sh`、記録：`Exp4/search_queue.log`
  - 注意：`load_model()` は読み込み後に乱数の seed を現在時刻で設定し直すため、探索フェーズは厳密には再現できない
- 参考：探索空間の FLOPs の範囲は 25.6M（すべて Zero / 3x3_MBConv3）〜 187.8M（すべて 7x7_MBConv6）。制約なしの探索結果は 148.5M
- β = 0.3 は 1 回目、1 エポック目の検証へ移る瞬間に nvrtc のセグメンテーション違反で落ちたため、再実行した（10-07 16:58〜17:53）
- **結果**（10-07 15:36〜17:53）

| β | 構造の FLOPs | パラメータ数 | supernet 検証（最終 / 最高） | α のエントロピー |
|---|---|---|---|---|
| 制約なし（5.4） | 148.5M | 2.19M | 82.1% / 82.9% | 1.39 |
| 0.3 | 141.9M | 2.19M | 81.8% / 82.4% | 1.34 |
| 1.0 | 95.7M | 1.51M | 82.0% / 82.4% | 1.12 |
| 3.0 | 55.3M | 1.27M | 80.5% / 81.4% | 0.82 |

  - β を強くするほど、supernet の精度をあまり落とさずに構造が小さくなり、α も収束しやすくなる
  - FLOPs はカーネルを小さくするのではなく、ブロックの省略（Zero、β = 3.0 では 11 ブロック）と拡張率の低下（6 → 3）で減らしている。7×7 カーネルは残る
  - 構造の違い（21 ブロック中）：制約なし vs β = 3.0 が 12、β = 1.0 vs β = 3.0 が 8、制約なし vs β = 1.0 が 7、制約なし vs β = 0.3 が 3
- **次の段階の案（総 FLOPs を約 290M にそろえた比較、すべてスクラッチ）**：S = β 3.0 の構造（55.3M）、M = β 1.0 の構造（95.7M）、L = 制約なしの構造（148.5M）として
  - 大きさ混合 S + M + L（299.5M）／ M × 3 seed（287.2M、基準）／ L × 2 seed（297.0M）／ S × 5 seed（276.3M）
  - L は `Exp3/scratch/arch00_s0`・`arch00_s1` を流用。新たに S × 5、M × 3 の 8 モデルを学習（約 4〜5 時間の見込み）
  - 探索空間の最大は 187.8M なので、約 290M の単体モデルは作れない（計画 C で `--width_mult` を上げる必要あり）
- 次の段階：得られた大きさの違う構造を組み合わせ、総 FLOPs をそろえたアンサンブルを seed アンサンブル・単体モデルと比べる
- 1 回の探索の中で FLOPs の範囲を変えて取り出す方法（`cifar10_derive_archs.py --min_flops / --max_flops`）も、追加の探索なしで試せる
- `cifar10_arch_search.py` に `--flops_target`（MFLOPs）を追加した。`mul#log` ではほぼ効果がないが、`add#linear`（λ (FLOPs − T) / T）では罰則の強さが T に反比例するので使い道がある

**C. FLOPs をそろえた単体モデル（約 450M、1 モデル 1〜2 時間）**
- 目的：アンサンブル（合計約 450M FLOPs）と同じ計算量を、1 つの大きなモデルに使った場合との比較。どの主張にも必要
- 方法の候補：探索時の `--width_mult` を上げる、または FLOPs 目標 450M で探索する

## 7. 論文に書くべき点

### 7.1 元の手法からの変更（手法・実験設定の節に明記）
- **CIFAR-10 向けの supernet 変更**：stem stride 2→1、第 1 段 stride 2→1（最終特徴マップ 4×4）
- **ハードウェア制約**：mobile レイテンシ表は 224 入力専用なので FLOPs を使用。基準値は公式構造の FLOPs 比（0.28〜0.30）から ImageNet の値を換算
- **実装の修正**：公開実装の `ArchGradientFunction` は、現在の PyTorch では探索フェーズで候補演算の重みに勾配を渡さない。修正して実験したことを再現性のために明記する（元論文当時の環境での挙動は未確認なので、元論文の結果に対する主張はしない）
- **FairNAS 型ウォームアップ**：FairNAS [15] の strict fairness をウォームアップに適用。次の 2 点は FairNAS からの変更として明記する
  - 勾配を、そのパラメータが使われた回数で割る（FairNAS は単純な和。この設定では和にすると最初の 10 ステップで損失が平均 22 まで発散した）
  - 候補数が層によって 6 / 7 と異なるため、6 候補の層では 1 候補だけ 2 回使う
- **ウォームアップの長さ**：エポック数ではなく更新ステップ数で ImageNet 設定と比較して決めたことを書く（CIFAR-10 は 1 エポックのステップ数が約 1/29）
- **NEAS の Diversity Score の転用**：NEAS [4] は層ごとの演算の組み合わせを評価して、supernet 学習中に探索空間を縮める。本研究では同じ DPP カーネルを**構造単位**で使い、**再学習の前に**似た候補を棄却する。この違いは明記すること
- **γ の扱い**：NEAS の式では γ は品質にかかる定数倍だが、同じ個数の組み合わせを比べる限り det は γ^{2K} 倍されるだけで選ばれる組み合わせが変わらない。そこで本実装では指数（r^γ）とし、精度と多様性の重みを調整できるようにした
- **類似度の特徴**：NEAS は各パスの出力特徴マップ、本実装は最終層直前の 1280 次元特徴を使う。β は中央値ヒューリスティックで自動設定
- **品質の評価データ**：学習データのうち、検証用とは別の 2,000 枚（NEAS の ACC_train′ に相当）。検証データはアンサンブルの組み合わせ決定用に使わずに残す
- **BN 再計算**：継承重みで評価する前に、各候補の BN 統計を学習データで再計算する
- **選択アルゴリズム**：det を最大化する部分集合は貪欲法で近似（DPP の MAP 推定 [6, 8]）

### 7.2 コスト比較で報告すべき指標
- 探索時間は 1 回分で、K 個取り出してもコストは増えない（fair ウォームアップ込みの時間を報告する）
- 再学習は 1 モデル約 45 分なので、K 個なら約 45K 分。総コストは探索 + 再学習で比べる
- DPP による選択そのものは候補 12 個で約 16 秒（再学習に比べて無視できる）
- 精度は **総 FLOPs・総パラメータ数をそろえた条件**で、単体モデルと比較する
- 比較対象：(a) 探索で得た単体の最良構造、(b) **同じ構造を seed だけ変えたアンサンブル（必須。5.7 ではこれと差が出なかった）**、(c) seed を変えて K 回探索した構造のアンサンブル、(d) `topk` / `order` で選んだ構造のアンサンブル
- アンサンブルのメンバーは**スクラッチから学習した条件で比べる**。supernet の継承重みから始めると、メンバーの誤りが似てアンサンブルの効果が半分程度になる（5.8）
- 差が小さいので、seed を変えた繰り返しで平均と標準偏差を示す
- supernet 学習の比較（一様ランダム vs fair）は、エポック数ではなく計算時間をそろえて示す（4.5 節）

### 7.3 多様性の指標
- 予測の食い違い率 [13] と oracle 精度は `cifar10_ensemble_eval.py` が出力する
- アンサンブルの NLL も報告すると、較正の観点からの比較ができる [10]

### 7.4 提案手法の位置付け（新規性・手法の定義・名前の案）

**NEAS との違い（3 つの軸）**

| 軸 | NEAS [4] | 本手法 |
|---|---|---|
| 単位 | 層ごとの演算の組み合わせ | **構造全体** |
| タイミング | supernet の学習中（探索空間を縮める） | **探索の後、再学習の前** |
| 前提となる探索 | アンサンブル専用の K-path supernet と進化探索 | **通常の 1 回の探索**（ProxylessNAS、勾配法）の確率 α をそのまま使う |

「DPP で分析する対象をモデルに変えた」とだけ書くと小さな変更に見えるので、**いつ・何のために使うか**まで含めて定義する。

**主張できる貢献の候補**
1. **1 回の探索から、再学習なしで多様なメンバーを選ぶ仕組み**（中心となる新規性）
   - 探索で得た α から候補を作り、supernet の継承重みだけで品質と多様性を測って、再学習する K 個を DPP で選ぶ
   - コストの大半を占める再学習の前に、似た候補を捨てられる
   - アンサンブル専用の supernet（NEAS）や、学習済みモデルの大きな候補群（NES [5]）を必要とせず、既存の one-shot NAS に後付けできる
2. **品質の重み γ の定式化の修正**（小さな技術的貢献）：NEAS の定数倍の γ は、同じ個数の集合を比べる限り選択に影響しない。指数に改め、品質と多様性のバランスを調整できるようにした（7.1）
3. **分析としての知見**（手法の新規性ではないが、貢献として書ける）
   - アンサンブルのメンバーは supernet の重みを引き継ぐと多様性が下がり、効果が約半分になる（5.8）
   - CIFAR-10 で one-shot NAS を使うときの更新ステップ数の問題と、FairNAS 型ウォームアップの有効性（4 章。バグ修正は再現性の情報として書く）

**注意**
- 現時点（5.7）では、スクラッチの条件で dpp と seed 違いのアンサンブルに差が出ていない。中間発表では「**手法の提案と予備的な結果**」と位置付け、計画 B（6.2、大きさの違う構造の混合）を今後の検証として示す
- 「DPP でアンサンブルのメンバーを選ぶ」発想自体は、NAS の外（アンサンブル pruning など）に先行研究がある可能性がある。予稿に新規性を書く前に、"determinantal point process ensemble selection" などで調べておく

**手法の定義（予稿用の例）**

> **提案手法**：1 回の one-shot NAS で得たアーキテクチャ分布から，再学習の前にアンサンブルのメンバーを選択する．
> 1. FairNAS 型ウォームアップで supernet を学習し，ProxylessNAS の勾配法でアーキテクチャパラメータ α を学習する（必要に応じて FLOPs 正則化の強さ β を変える）
> 2. softmax(α) から P 個の候補アーキテクチャをサンプリングする
> 3. 各候補を supernet の継承重みで構成し，BN 統計を再計算したうえで，品質 r_p（学習データの部分集合での精度）と特徴の類似度 S_pq を測る
> 4. L = diag(r^γ) S diag(r^γ) に対して det(L_Y) を貪欲法で最大化し，K 個を選ぶ
> 5. 選んだ K 個をスクラッチから学習し，softmax の平均で予測する

**英語名の案**（メンターからの提案を受けて検討）

| 名前 | 由来 | 印象 |
|---|---|---|
| **PRISM**（第一候補） | **P**re-**R**etraining **I**nherited-weight **S**election of diverse **M**odels | 1 本の光（1 回の探索）がプリズムで多様な色（モデル）に分かれる比喩が、手法の内容と一致する |
| DiPS | **Di**versity-aware **P**ost-search **S**election | 短く、何をするかがそのまま伝わる |
| SOMA | **S**earch **O**nce, ensemble **M**any **A**rchitectures | 「1 回の探索で多数」というコスト面の主張を前面に出せる |
| KALEIDO | **K**-architecture **A**ssembly via **L**og-det **E**nsemble **I**nherited-weight **D**iversity **O**ptimization | 印象には残るが、頭字語としては少し無理がある |

- PRISM は機械学習の分野ですでに何度も使われている名前。中間発表では問題ないが、論文では "PRISM-NAS" などで区別するか、DiPS のような短い名前を選ぶ。決める前に同名の手法がないか検索する

### 7.5 予稿の表の作り方

- **丸め**：表の値は小数第 3 位で四捨五入して 2 桁。JSON の `10.01999999…` のような値は単精度浮動小数点数の誤差で、正確な値は枚数から計算する
- **最良値の太字**：表示上同じ値は両方太字にする。例：スクラッチの食い違い率（テスト）は seed 10.020%（3 ペア合計 3006 枚）、dpp 10.0167%（3005 枚）で、差は 30,000 回の比較中 1 枚。2 桁表示ではどちらも 10.02 なので両方太字にする（3 桁表示にすると意味のない差を強調してしまう）
- 同じ食い違い率でも、検証データでは dpp 9.96% > seed 9.84% と順位が入れ替わる。seed と dpp の多様性は「同程度」と書くのが正確。dpp と topk の比較（テスト 10.02% 対 9.68%、検証 9.96% 対 9.43%）なら、どちらのデータでも dpp が上
- **方向の表示**：列名に「Acc. ↑」「NLL ↓」「食い違い率 ↑」「FLOPs ↓」と付けると読みやすい
- **FLOPs の列**：比較の条件がそろっていることを示す列なので、太字にしない。本文で「各アンサンブルの総 FLOPs はおおむね同程度（差は最大約 4%）」と一言添える。スクラッチの topk は精度が最も高い（92.57%）が、総 FLOPs も約 4% 多い（464.7M 対 445.5M）
- **FLOPs の単位**：このコード（`utils/pytorch_utils.py` の `count_conv_flop`）の値は積和演算（multiply-accumulate）の回数で、BN と活性化関数は含まない。ProxylessNAS や NEAS では慣例的に「FLOPs」「MFLOPs」と書く（NEAS の図 1 の軸名は "Millions of Multiply-Adds (MFLOPs)"）。予稿では列名を「MACs」にするか、注に「積和演算の回数（ProxylessNAS [1] の計数方法）」と書く
